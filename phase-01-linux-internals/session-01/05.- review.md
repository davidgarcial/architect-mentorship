# Session 01 — Dockerfile Security Review

## Finding-by-Finding Evaluation

### USER root
**Status: CORRECT — chain depth 3**
K8s chain is solid: RCE → root shell → docker socket → host filesystem → kubelet creds → cluster takeover.
Gap: docker socket path only works if the socket is mounted — that's a configuration dependency, not a given.

---

### appuser NOPASSWD:ALL sudoers
**Status: CORRECT — chain depth 3**
Chain: get appuser shell → `sudo su -` → root.
`USER appuser` in the Dockerfile is meaningless with this sudoers entry.

---

### netcat / wget / curl
**Status: CORRECT — chain depth 2**
Tools and attacker use identified (reverse shell, payload download).
Missing next step: RCE → `nc -e /bin/bash` → interactive shell → `wget` pulls next-stage payload.

---

### Hardcoded SSH root password
**Status: CORRECT — chain depth 2**
Layer exposure via `docker history` correctly identified.
Missing end state: attacker SSHes in as root → full root shell, no exploit needed.

---

### chmod -R 777
**Status: CORRECT — chain depth 3**
Persistence chain correct: any shell → overwrite `app.py` → backdoor runs on next container restart.

---

### pip install without --require-hashes
**Status: CORRECT — chain depth 2**
Both paths named (typosquatting, dependency confusion) and `setup.py` RCE explained.
Missing end state: attacker controls the image, bakes in a backdoor, exfiltrates build-time secrets.

---

### SSH host keys baked into image
**Status: CORRECT — chain depth 1**
Problem described but no attacker chain written.
Missing: attacker records fingerprint from one container → MITM any other container from same image without triggering SSH client warnings.

---

### Port 22 / EXPOSE 22
**Status: INCOMPLETE — depth 1**
Observed "do we need both ports?" but never answered.
Real finding: `sshd` running as an app service in a container is wrong in principle.
Note: `EXPOSE` does not open a port — removing it without removing `sshd` from CMD means SSH still runs, just undocumented.

---

## Missed Findings

| # | Hint |
|---|---|
| 1 | The base image itself is the finding — ubuntu:22.04 ships ~400 packages; everything extra is attack surface that disappears for free by switching to a minimal image. |
| 2 | `useradd` is missing two hardening flags — what happens if an attacker leaks credentials for a user whose shell is `/usr/sbin/nologin`? |
| 3 | PID 1 is bash, not the application — what happens to the container's lifecycle when `app.py` crashes? |
