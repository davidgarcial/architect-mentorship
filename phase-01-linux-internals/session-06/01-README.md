# Phase 01 — Linux Deep Internals | Session 06 of 12

## Topic
cgroups: resource limits and security implications

## Session Goal
Recognize that missing resource limits are not just an operational problem — they are an availability attack vector, and in multi-tenant environments they are a form of privilege escalation against other workloads on the same node.

## The Artifact
A Kubernetes Deployment YAML for a production API service with two containers — the API itself and a Redis sidecar. Neither container has a `resources` block. This is not a contrived example; it is the default state of most YAML generated by `kubectl create deployment` and scaffold tools. The absence of limits has security implications beyond "it might use too much memory."

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-service
  template:
    metadata:
      labels:
        app: api-service
    spec:
      containers:
      - name: api
        image: myapp:latest
        ports:
        - containerPort: 8080
        # No resources block — no limits, no requests
      - name: redis
        image: redis:7
        ports:
        - containerPort: 6379
        # No resources block
```

Your task is to enumerate every security implication of the missing `resources` block — not just "it could OOM" — and write the corrected YAML with appropriate limits, requests, and a LimitRange to enforce minimums cluster-wide.

## Background (read after attempting the artifact)
- **What cgroups do:** Control groups (cgroups) are a kernel mechanism that limits, accounts for, and isolates resource usage (CPU, memory, disk I/O, network bandwidth, PIDs) for a collection of processes. When Kubernetes sets a container's resource limits, it translates those into cgroup parameters on the node. Without a limit, the cgroup has no constraint — the container's processes can consume as much of the resource as the node has available.
- **The OOM kill cascade:** When a node runs out of memory, the Linux kernel's OOM killer terminates processes to recover memory. Without memory limits, the OOM killer chooses victims based on OOM score — it tends to kill large, non-system processes. This means an unbounded container that consumes all node memory can cause the OOM killer to evict other containers on the same node, including unrelated workloads. This is an availability attack against co-located services even if the consuming container is not malicious.
- **Scheduler placement and noisy neighbor:** Kubernetes places pods on nodes based on resource requests, not limits. A container with no requests is treated as if it requests zero resources — it can be placed on any node, including nodes already near capacity. Multiple no-request pods pile onto the same node until the node collapses. This is why `requests` matter for scheduling correctness: they tell the scheduler what the pod actually needs, preventing placement on nodes that cannot serve it.
- **PID limits and fork bombs:** Without a PID limit cgroup, a container process can fork until the node's PID table is exhausted. The kernel's PID table is a global resource (typically 32768 or 4194304 PIDs). Exhausting it means no new processes can be created anywhere on the node — not by the container runtime, not by the kubelet, not by system services. The node becomes effectively unmanageable. Kubernetes sets a default `pids-per-pod` limit on newer versions but it depends on kubelet configuration. The YAML above has no explicit PID limit.
- **Resource starvation as an availability attack:** In a multi-tenant cluster (multiple teams sharing one cluster), a team's unbounded workload can starve another team's workload of CPU or memory without any explicit attack. This is not theoretical — it is a common incident cause in shared clusters. A security architect must require LimitRange and ResourceQuota policies that prevent any workload from running without declared limits.

## Exercise

### Step 1 — Model the attack scenarios
Without running anything, reason through and document the following scenarios with specific, concrete impact statements:

**Scenario A — Memory exhaustion:** The `api` container has a memory leak. It consumes memory until the node's free memory is below the threshold that triggers OOM. Which pods get killed? How does this affect the `api-service` pods on the same node? What happens to unrelated pods on the same node?

**Scenario B — CPU starvation:** One of the three `api-service` replicas enters a CPU-intensive loop (e.g., a malformed JSON payload triggers a ReDoS — Regular Expression Denial of Service). Without CPU limits, how much CPU can it consume? What happens to the other two replicas on the same node?

**Scenario C — Fork bomb via code execution:** An attacker exploits an RCE vulnerability in the API and runs a fork bomb. Without a PID limit, what is the impact on the node?

**Scenario D — Scheduler misplacement:** Kubernetes schedules all three replicas on the same node because the node appears to have capacity (requests are zero, so the scheduler sees zero resource consumption). What is the blast radius of a node failure in this configuration?

### Step 2 — Write the hardened YAML
Add a `resources` block to both containers with appropriate `requests` and `limits`. Use these rules:
- `requests` should reflect what the container needs to function normally (this is what the scheduler uses)
- `limits` should be the ceiling the container should never exceed (this triggers throttling for CPU, OOM kill for memory)
- Memory limit should be 1.5–2x the memory request (allows for bursting without immediate OOM)
- CPU limit is optional but recommended — CPU throttling is preferable to CPU starvation of neighbors

Also write a `LimitRange` manifest that enforces default limits on any container in the namespace that does not declare its own:
```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: production
spec:
  limits:
  - type: Container
    default:
      memory: "256Mi"
      cpu: "500m"
    defaultRequest:
      memory: "128Mi"
      cpu: "100m"
    max:
      memory: "2Gi"
      cpu: "2"
```

### Step 3 — Verify cgroup enforcement
If you have a Kubernetes cluster or `minikube` available, apply the YAML and verify the cgroup limits are set on the node:
```bash
# Find the container's cgroup path
docker inspect <container_id> | grep CgroupParent
# or in Kubernetes:
kubectl get pod <pod-name> -o jsonpath='{.status.containerStatuses[0].containerID}'

# On the node, check the memory limit cgroup
cat /sys/fs/cgroup/memory/<cgroup_path>/memory.limit_in_bytes

# Check the CPU shares
cat /sys/fs/cgroup/cpu/<cgroup_path>/cpu.shares
```
Alternatively, demonstrate with Docker directly:
```bash
# No limits
docker run -d --name unlimited redis:7
cat /sys/fs/cgroup/memory/docker/<container_id>/memory.limit_in_bytes
# Returns: 9223372036854771712 (max int64 — effectively unlimited)

# With limits
docker run -d --name limited --memory=256m --cpus=0.5 redis:7
cat /sys/fs/cgroup/memory/docker/<container_id>/memory.limit_in_bytes
# Returns: 268435456 (256 MiB in bytes)
```

## Offline Notes
- `/sys/fs/cgroup/memory/` — cgroup v1 memory controller. `/sys/fs/cgroup/<pod_id>/memory.max` in cgroup v2.
- `docker stats` — live view of CPU/memory usage and limits per container
- `kubectl top pods` — resource consumption view (requires metrics-server)
- `kubectl describe node <node>` — shows Allocatable resources and current requests/limits from all pods
- Kubernetes QoS class determination: Guaranteed = all containers have equal requests and limits; Burstable = at least one container has a request or limit; BestEffort = no containers have requests or limits
- The OOM killer uses `/proc/<pid>/oom_score_adj` to bias which processes get killed. Kubernetes sets this differently for Guaranteed vs BestEffort pods.
- `man 7 cgroups`, Linux kernel docs: https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html
- ResourceQuota limits total resource consumption across a namespace, LimitRange sets per-container defaults — both are needed for complete enforcement
